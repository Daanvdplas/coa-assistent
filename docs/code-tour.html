Follow a question through the code

The web model can call one local Rust search tool. Rig runs that loop; the application checks the returned source quotes before showing the answer.

Start with the sources

The application entry point loads demo-twelve before starting the server. Corpus selection keeps the earlier five- and ten-document versions separate so saved experiments retain their source identities.

Index::load_for_corpus parses twelve fictional activity documents into 72 sections. It embeds each document title, heading and exact section text locally with multilingual MiniLM through fastembed 7.1.2. Each 384-number vector remains paired with its original text, document ID and source date in RAM. The disk cache contains model files, not a persistent web vector database.

One question, from click to tool call

Where and when can I garden?

This example follows the actual code path; it does not replay a newly measured answer. In demo.js, submitting the form sends the question, answer language, search method and top_k: 3 to POST /api/runs. web::run → start checks capacity and session limits, writes a pending run to RunStore, then starts asynchronous work. The browser receives the run ID immediately and polls it.

web::serve connects the model to the index through this callback:

let search: Search = Arc::new(move |query, top_k, method| {
    index
        .lock()
        .map_err(|_| "Zoekindex is niet beschikbaar.")?
        .search_for_method(query, top_k, method)
});

The important connection is search_for_method: a normal Rust function call against the shared index. SearchTool::execute_inner runs it on a blocking worker and records the real query, public search goal and returned passages. Rig controls the conversation with Sol. Its policy hook requires the first search, allows focused follow-up searches and stops further tool use at four searches.

The model/tool wiring
let agent = AgentBuilder::new(model)
    .preamble(instructions)
    .tool(SearchTool { /* shared search callback and run state */ })
    // output schema, token limits and policy hook are configured here
    .build();

let response = agent
    .prompt(query)
    .max_turns(MAX_PROVIDER_REQUESTS)
    // invalid tool calls are not retried
    .await;

Abbreviated from rig_runtime::run. The application supplies the tool and policy; Rig owns the model/tool loop. Each request still passes through the application's bounded HTTP transport.

What the search returns

With meaning-based search, Index::search_with_top_k embeds the model's search query and ranks sections by cosine similarity. BM25 instead scores matching words. Index::search_for_method binds either route to the selected method. Sol receives the returned text and its provenance, not the embeddings.

The gardening source has the Tuesday 10:00–12:00 schedule in S2 and the fictional address in S3. A first search may omit one. Sol can then request a narrower search, but the loop does not guarantee complete retrieval. The recorded 13 November smoke test missed the address and left it unknown.

Source publication dates, schedules and availability observations remain separate. The gardening document is dated 20 October; its last place-count observation is 1 September. Neither establishes free places today.

Check provenance before success

validate_retrieved_answer is shared validation code, despite living in a file named codex.rs. It requires successful real search evidence and validates the structured answer. Each citation's exact quote must occur in the returned section with the same document ID, section ID and date.

The web worker also compares the returned corpus manifest, source list, reference date and search method with the run's original context. It then completes the run in RAM. Browser polling receives either the answer with citations and real search actions, or a bounded error.

A valid quote proves where quoted words came from. It does not verify every conclusion or prove that no suitable activity was missed. The staff member and resident still make the practical decision.

Bound the external work

BoundedTransport::request reserves an attempt in the durable budget, then counts the complete input through OpenAI before generation. Unknown counts or inputs above 300,000 tokens stop there. Successful preflight sends the original generation payload unchanged. Each question permits at most five model attempts, four searches and 120 seconds; output is capped at 4096 tokens per attempt. HTTP retries are disabled.

The web server permits ten concurrent questions and one active question per session. RunStore keeps bounded history in RAM with a 30-minute inactivity lifetime. Restarting clears that memory but preserves the separate attempt budget. Keys and budget files stay outside the repository. See local setup for configuration and the runtime report for public hosting and the cost calculation.

Full request sequence
Browser → Rust: POST question, language and method
Rust → RunStore: begin pending run; return run ID
Rig → budget: reserve one attempt
Rig → OpenAI: count complete input
OpenAI → Rig: count; reject if unknown or too large
Rig → OpenAI: generate with original payload
OpenAI → Rig: search request
Rig → local Rust index: query and fixed method
Index → Rig: source sections and dates
Rig → OpenAI: next counted model attempt with tool result
OpenAI → Rig: final structured answer
Rust: validate quotes, source identity and run context
Rust → RunStore: complete or fail
Browser → Rust: poll run ID and show result

The model exchange repeats only within the fixed limits. The Mermaid sequence source and architecture source describe this same web route.
