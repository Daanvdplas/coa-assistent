COA Assistent Demo How it works

Search first. Then answer.

The assistant retrieves text from twelve fictional activities before answering. You can inspect the passages that support its answer.

  1. 1. You ask a questionAbout a time, location or language support, for example.
  2. 2. The assistant searchesA local search function retrieves passages. It can search again.
  3. 3. You check the sourceThe answer shows quotes with the activity and source date.

Where and when can I garden?

This question needs two pieces of text: the time and location of the same activity. The search function passes retrieved text to the answer model. That model can make a more focused search if something is missing.

The fictional gardening source records the time in Dutch:

Iedere dinsdag van 10.00 tot 12.00 uur.
Gardening · section S2 · source date 20 October 2026

That means Tuesday, 10:00–12:00. An initial search may miss the address. Searching again can help, but does not guarantee a complete answer. Missing information should remain unknown. An old number of free places does not establish availability today.

How does search find the text?

The twelve documents contain 72 sections. Each keeps its activity, heading and source date. MiniLM locally turns the text into a list of numbers: an embedding. Meaning-based search compares these with the search query's numbers, so related words can lead to the same passage.

The demo also offers word-based search with BM25. It considers matching words and how distinctive they are. Neither search score is a probability that an answer is correct. Search can return related text even when the requested fact is missing.

What does the assistant check?

Sol writes the answer using retrieved text. The application then checks that each quote occurs exactly in an actual retrieved passage from the right activity, section and date. You can inspect those passages and the searches that were performed.

A valid quote establishes where the words came from. It does not prove every conclusion or show that all suitable activities were found. A staff member checks the sources and discusses the options with the resident.

How do the model and search function work together?

The Rust app uses Rig to call Sol through the OpenAI Responses API. The model has one tool: search_document. It calls the local Rust search function directly. The first search is required; the model can then make focused follow-up searches.

Question → Rig and Sol → local search
                         ↓ source passages
             Sol → answer → quote validation

A question may use at most four searches and five model attempts within 120 seconds. Before each attempt, OpenAI counts the complete input. An unknown count or more than 300,000 input tokens blocks generation. A persistent budget limits the total number of attempts.

What stays local, and what leaves?

Source sections, embeddings and search computation stay on the server. OpenAI processes your question and retrieved passages to write an answer. Public-demo traffic passes through Cloudflare. Use fictional information only.

Questions and answers live temporarily in server memory. Inactive sessions expire after thirty minutes when cleanup next runs. That does not automatically remove data held by external services. The demo does not update resident records, send messages or register anyone. Participation remains the resident's choice.

The server and the separate evaluations

The ordinary demo keeps its index in RAM, without a database. Model files are cached locally. One Rust program serves the website and calls the search function; the web route starts no Codex or MCP processes. OpenAI receives text, not embedding vectors.

The separate CLI and model experiments do use Codex with a read-only MCP search tool. Evaluation tools use TypeScript and promptfoo. Optional SQLite storage and additional search methods belong to those experiments, not the ordinary web demo.

What do we know about quality?

Retrieval evaluations check whether the required source passages were actually found: a time and location for one valid activity, for example. That differs from checking the written answer. Answer quality has not yet been validated against human reference judgments.

Saved comparisons use earlier source sets and the Codex route. They do not measure the current Rig demo's quality. The Rig route was checked with three fictional questions on twelve sources; one address was missed. Working software does not mean every source fact is found.

What exactly do the evaluations measure?

Expected source combinations stay outside the search index and model input. Fixed code scores them afterwards. When several activities are valid, a complete combination for one activity counts; the time of one and location of another do not form a valid combination.

Local tests with mock models also check citation errors, bounded usage, session isolation and ten concurrent questions. They do not prove current OpenAI capacity. Provenance, completeness and answer quality remain separate properties.
